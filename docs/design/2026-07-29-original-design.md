# State Managers Comparison — дизайн

Дата: 2026-07-29
Статус: черновик на утверждении

## Задача

Публичный репозиторий, в котором одно и то же нетривиальное приложение реализовано пять раз — по разу на каждый стейт-менеджер. Цель: измеримое сравнение по трём осям — сложность, скорость, стоимость поддержки.

Вторая цель, влияющая на решения не меньше первой: репозиторий работает как портфолио для HR и нанимающих менеджеров. Отсюда требования к README, живому демо и воспроизводимым цифрам вместо мнений.

## Участники сравнения

| Библиотека | Парадигма | Что именно проверяем |
|---|---|---|
| RxJS | Потоки | Высокочастотные апдейты, backpressure, temporal-операторы |
| Redux Toolkit | Централизованный flux | Нормализация, listener middleware, boilerplate против предсказуемости |
| MobX | Прозрачная реактивность | Точечная инвалидация, `reaction`, «магия» как риск поддержки |
| Zustand | Минималистичный hook-store | Ручные селекторы, цена простоты на масштабе |
| Jotai | Атомы bottom-up | Гранулярность, композиция производных атомов, `atomEffect` |

Пятёрка подобрана как спред парадигм, а не как набор похожих библиотек. Пять вариаций одного подхода не дали бы разброса в измерениях.

Сознательно не берём: Recoil (проект закрыт), XState (моделирование логики, а не хранение состояния — другой класс инструмента), Effector (сильная библиотека, но узкая география найма, что противоречит второй цели).

## Эталонное приложение

**TraderCat Lite** — торговый журнал и терминал. Домен взят из реального продукта пользователя, чтобы код был переиспользуем, а не выброшен после публикации.

Два экрана намеренно нагружают состояние по-разному:

### Экран 1. Терминал (высокочастотное состояние)

- Поток котировок по ~50 инструментам, 10/50/100 обновлений в секунду (переключается в UI)
- Таблица инструментов: сортировка, фильтр, подсветка изменения цены
- Открытые позиции: нереализованный P&L пересчитывается на каждом тике
- Сводка по счёту: суммарный P&L, использованный риск, текущая просадка
- Панель инструмента с историей цены за сессию

### Экран 2. Дневник (нормализованное состояние и агрегаты)

- ~250 закрытых сделок из фикстуры
- Фильтры: период, монета, стратегия, направление, результат
- Агрегаты: кривая доходности, винрейт, R-multiple, профит-фактор, максимальная просадка, время в сделке
- Редактирование сделки: тег стратегии и заметка, оптимистичный апдейт с откатом при ошибке

### Сквозной сценарий. Движок алертов

Правила из реального продукта, работающие поверх обоих экранов:

- Дневной лимит убытка превышен
- Риск на сделку больше лимита
- Серия убытков за короткое окно (тильт)
- Позиция открыта дольше, чем в N раз превышает обычное время удержания

Это ядро сравнения. Правила требуют временнóй логики, чтения нескольких срезов состояния сразу и запуска побочных эффектов ровно один раз на переход. Каждая библиотека решает это принципиально по-своему, и различия видны в коде без интерпретации.

### Границы

Бэкенда нет. Никакого подключения к бирже, никакой авторизации. Фид котировок — детерминированный генератор с фиксированным seed, сделки — статичная фикстура. Иначе проект превратится в фуллстек-приложение и перестанет быть сравнением стейт-менеджеров, а замеры потеряют воспроизводимость.

## Архитектура

npm workspaces (не pnpm — его нет в системе; не bun — для портфолио важна предсказуемость установки у любого проверяющего).

```
state-managers-comparison/
├── packages/
│   ├── domain/     Типы, генератор фида, фикстуры, чистые расчёты
│   ├── ui/         Презентационные компоненты без состояния
│   └── bench/      Playwright-харнесс, сбор метрик, генератор отчёта
├── apps/
│   ├── rxjs/  redux/  mobx/  zustand/  jotai/
├── docs/
└── .github/workflows/
```

Стек: React 19, TypeScript strict, Vite.

### Ключевое архитектурное решение

**Всё, кроме слоя состояния, — общее.** Доменные типы, вся арифметика P&L и статистики, все компоненты отображения живут в `packages/`. Приложения различаются исключительно тем, как состояние хранится, выводится и распространяется.

Без этого правила сравнение не работает: разница в LOC отражала бы разный UI-код, а разница во времени рендера — качество моих компонентов, а не свойства библиотек.

Отдельно важно, что расчёты P&L и статистики лежат в `packages/domain` как чистые функции. Иначе замеры показали бы разницу в моей математике, а не в стейт-менеджерах.

### Граница между общим кодом и приложениями

Общего TypeScript-интерфейса, который обязаны реализовать все пятеро, не будет. Такой интерфейс силой привёл бы все библиотеки к одной форме и уничтожил бы ровно те различия, которые проект измеряет.

Вместо этого контракт задаётся тремя вещами:

1. Один и тот же список фич (выше)
2. Одно и то же дерево компонентов из `packages/ui`
3. Один и тот же набор `data-testid`

Третий пункт позволяет одному Playwright-сценарию без изменений прогонять все пять приложений.

## Метрики

### Скорость

| Метрика | Как снимается |
|---|---|
| Задержка тик → отрисовка, p50 и p95 | `performance.mark` в генераторе фида, `requestAnimationFrame` после коммита |
| Число ре-рендеров на тик | Инструментированные обёртки компонентов, счётчик в `window` |
| Long tasks (>50 мс) за 60 с прогона | `PerformanceObserver` |
| JS heap после 60 с | CDP `Runtime.getHeapUsage`, проверка на утечки |
| Размер бандла, gzip | `rollup-plugin-visualizer`, отдельно дельта слоя состояния над общей базой |
| Cold start до интерактива | Playwright-навигация |

Прогон при 10, 50 и 100 upd/s. Три повтора, берётся медиана.

### Сложность

- LOC слоя состояния (только `apps/*/src/state`, общий код исключён)
- Цикломатическая сложность
- Число различных экспортов библиотеки, использованных в слое состояния — счётная замена расплывчатому «сколько концепций надо выучить»
- Число файлов, затронутых типовым изменением

### Стоимость поддержки

Измеряется экспериментом, а не мнением: после того как все пять реализаций готовы и зафиксированы тегом, в каждую добавляется одна и та же новая фича — алерт «приближение к дневному лимиту». Замеряется размер диффа, число затронутых файлов и число мест, где потребовалось менять уже работающий код.

Дополнительно:

- Ловит ли компилятор все поломки при изменении доменного типа
- Качество devtools и воспроизводимость отладки (описательно, с честной пометкой, что это субъективно)
- Число зависимостей и вес транзитивного дерева

## Тестирование

- Vitest на чистые функции в `packages/domain` — общая математика обязана быть верной, иначе цифры бессмысленны
- По одному Playwright-сценарию на функциональный паритет, прогоняется против всех пяти приложений: одинаковый ввод должен давать одинаковый вывод. Без этого сравнение производительности некорректно — быстрая реализация может оказаться просто менее полной
- Тесты движка алертов на каждой реализации: правила срабатывают ровно один раз на переход
- Бенчмарки в CI не заваливают сборку по порогам: шум раннера сделал бы такой гейт бесполезным. Результаты публикуются как артефакт и как таблица

## Подача для HR

- GitHub Pages: живое демо с переключателем пяти реализаций на одном экране
- README на английском, русская версия отдельным файлом. Английский первым — это расширяет аудиторию нанимающих
- Таблица результатов генерируется из JSON бенчмарка, а не пишется руками. Заявление «цифры получены прогоном, а не набраны в таблице» проверяемо
- Раздел с выводами: когда какой менеджер оправдан. Без победителя — вывод «зависит от контекста, вот граница» читается сильнее, чем продвижение любимой библиотеки
- Отдельный документ с разбором движка алертов на пяти реализациях бок о бок — самая наглядная часть для технического интервью

## Порядок работ

1. `packages/domain` — типы, фид, фикстуры, расчёты, тесты
2. `packages/ui` — компоненты, Storybook не нужен
3. Референсная реализация на Zustand — самая простая, обкатывает контракт
4. Остальные четыре
5. `packages/bench` — харнесс и отчёт
6. CI, GitHub Pages, README

## Открытые вопросы

Нет. Все решения приняты; спорные помечены в тексте вместе с обоснованием.

## Риски

- **Пять реализаций — это много кода.** Митигация: общий UI и домен, слой состояния в каждой реализации остаётся небольшим
- **Бенчмарки в CI шумят.** Митигация: медиана из трёх прогонов, отсутствие жёстких порогов, публикация условий прогона
- **Обвинение в предвзятости.** Митигация: паритетные тесты, воспроизводимый харнесс, отсутствие объявленного победителя
